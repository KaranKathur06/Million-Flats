# Dynamic Search Hero Banners

## Model and Scope

`HeroBanner` stores one configuration per `scopeKey + category`. Scope is `CITY`, `COUNTRY`, or `GLOBAL`; categories are `BUY`, `RENT`, `PROJECTS`, and city-only `GENERIC`. City records reference the existing country-scoped `City` table. Country/global scope keys are generated by the admin API, not entered by an operator.

The existing property and project queries still store/filter city names as strings. The banner resolver resolves the selected city to the canonical City row when available, and the same resolver canonicalizes the city used by the result predicates. Unknown or ambiguous cities do not resolve to a city banner.

## Admin Workflow

Open **Admin → Website → Hero Banners**. Choose a city/category, country default, or global category. The city picker reads canonical database cities; use its add-city control to create another city in the existing City table. Save the text and scope, then upload desktop and optional mobile images. New configurations are inactive until activated from the list after preview.

Images are uploaded directly to the existing public S3/CDN flow using admin-only presigned URLs. The server verifies upload ownership, file size, MIME type, and decoded image dimensions with Sharp before storing the CDN URL and metadata. Unsupported/corrupt files are rejected. Aspect ratio differences are advisory, not blocking.

## Resolution and Fallback

For a selected canonical city, active banners resolve in this order:

1. City + requested category
2. City + Generic
3. Country + requested category
4. Global + requested category
5. Legacy built-in defaults if the database/resolver fails

Inactive, malformed, or missing-image records are skipped. Projects keep their existing gradient when the global Projects record has no image. Missing mobile art uses the desktop asset.

## Search Context

Buy and Rent routes resolve as `/buy` and `/rent`; `/properties` uses the existing `purpose` parameter (`purpose=buy|rent`). The existing `type` parameter remains the property-type filter and is not reinterpreted as Buy/Rent. The canonical city query is `location` on Properties (the legacy `city` query is accepted on initialization) and `city` on Projects. Country comes from the existing `country` parameter; absent values use the current India default for Properties, while Projects resolve an unambiguous canonical city without requiring a country parameter.

## Cache and Operations

Resolver results and canonical city lookups use Next `unstable_cache` with five-minute TTLs and explicit tags. Admin saves, status changes, image changes, and city creation invalidate the banner/city tags and the affected search routes. No new environment variables are introduced; existing AWS S3 and CDN configuration is reused.

## Image Notes

The provisional design targets are desktop 1920×450 and mobile 750×400. They are not hard validation limits. Confirm final rendered dimensions, crop/focal behavior, safe text area, and contrast overlay with design before producing the full city library. Headlines and subheadlines remain HTML; do not bake them into the image.

The public hero uses Next's configured AVIF/WebP image optimizer and responsive `srcSet`; media queries select the mobile composition so both assets are not downloaded together. Above-the-fold sources are preloaded with high fetch priority. An image error falls back to the legacy Buy/Rent artwork or the Projects gradient.

## Migration and Deployment

The migration adds the new table and indexes without changing existing search data, then seeds global Buy/Rent defaults with `/HOMEPAGE.jpeg` and a text-only global Projects default. Deploy with:

```powershell
npx prisma migrate deploy
npx prisma generate
```

After deployment, verify the defaults, then configure city banners gradually. No S3 bucket or CDN environment variables are new. If schema checks are performed before deploy, use the repository's current Prisma workflow and avoid `migrate dev` against production.
